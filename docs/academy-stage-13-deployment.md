# ETAPA 13 — Publicación y recuperación

No se publicó producción. El cierre está bloqueado por alertas altas de dependencias: no se considera un paquete listo para producción. Usar el artefacto que corresponda a la revisión aprobada y verificar sus hashes. No regenerar fixtures ni cambiar reglamentos del Scoreboard.

1. Validar externamente JwtSettings__Key (aleatoria, mínimo 32 bytes), JwtSettings__Issuer, JwtSettings__Audience y ConnectionStrings__bteConnection. No copiar secretos a appsettings del repositorio. El fail-fast informa únicamente el nombre faltante. FrontAccess__Key es obligatorio para el carrusel y debe coincidir con el frontend; esa clave pública no sustituye autenticación ni permisos.
2. Respaldar MySQL con el procedimiento operativo existente (`mysqldump --single-transaction --routines --triggers`), registrar SHA256 y comprobar espacio/salida. Mantener respaldo fuera del árbol web. Antes de modificar `/etc/bte-api.env`, respaldarlo con permisos restrictivos; esta etapa no lo modificó.
3. Deshabilitar/detener workers antes de migrar, conservando la cola histórica. Aplicar una sola vez, en orden, `bte_stage_13_history_restrict.sql`, `bte_stage_13_request_audit.sql`, `bte_stage_13_reset_token.sql` y `bte_stage_13_reset_token_index.sql`. DDL MySQL hace commit implícito: si falla, inspeccionar qué sentencia terminó y continuar desde allí. No reejecutar todo sin comprobar esquema.
4. Publicar backend. Los nuevos campos de api_log deben existir antes del binario. Mantener workers deshabilitados hasta revisar los 64 pendientes históricos. El log nuevo no guarda cuerpos, SQL ni detalles de excepciones. Los registros históricos sensibles requieren revisión/retención operativa; no se borraron datos de auditoría existentes.
5. Reiniciar bte-api.service solo durante el despliegue autorizado. Comprobar `/health/live` 200 y `/health/ready` 200; readiness devuelve 503 si MySQL no está disponible y no revela conexión. WhatsApp/Push opcionales no bloquean readiness. Swagger queda deshabilitado en Production salvo Swagger__Enabled=true explícito.
6. Publicar el frontend para `/bte/`. Verificar login, 401/403, scope, centro de avisos y mapas admitidos. URLs de mapas fuera de los embeds oficiales Google/OpenStreetMap se omiten. Verificar carrusel `GET /api/Events/upcoming` con Origin `https://budotournaments.net` y X-FRONT sin imprimir su valor.
7. Verificar confirmación/reembolso/promoción con datos de prueba autorizados. No hacer pruebas financieras en datos reales. Revisar errores por RequestId, ActorUserId y rutas, pendientes/fallidas por el mantenedor existente.

El rate limiter nativo es local por proceso: auth 10/min por IP de conexión, mutaciones sensibles 30/min por usuario autenticado. No confía en X-Forwarded-For del cliente. En un proxy se debe verificar su IP confiable antes de habilitar forwarded headers; sin ello, usuarios anónimos pueden compartir cuota del proxy. No se añadió Redis ni infraestructura de métricas. Bte.Api publica instrumentos request.duration/request.errors para un listener .NET; la captura/exportación es una tarea operativa separada.

La correlación devuelve X-Request-ID generado por el servidor. La metadata persistida conserva actor, ruta, estado y request ID; no reemplaza el historial de negocio: confirm/refund conservan actor/fechas y allocations, grados conservan history/override y retry queda asociado a la petición autenticada. Si no puede escribirse el audit log se emite advertencia y no se revierte el negocio.

Restauración: usar una base aislada NUEVA, sin apuntar nunca al esquema productivo. Importar el dump, comparar conteos/integridad y ejecutar pruebas allí antes de una recuperación real. No eliminar ni sobrescribir una base existente para simular restore. Para rollback de aplicación, detener workers y volver al binario previo manteniendo columnas adicionales y RESTRICT (compatibles). Revertir RESTRICT a CASCADE reintroduce pérdida de historial y no es un rollback recomendado. La recuperación de datos reales requiere decidir el punto de recuperación y probarlo primero en copia aislada.

Los cambios del código no invalidan secretos que hayan sido expuestos previamente. El operador debe rotar credenciales históricas fuera del chat y revisar historial/artefactos antiguos. No se rotaron claves del servidor ni sesiones en producción.

Antes de cualquier publicación, confirmar que las migraciones anteriores de ETAPAS 1–11 estén aplicadas en la base de destino; los cuatro scripts de ETAPA13 no crean ese esquema previo. Comparar constraints/columnas con la réplica validada. Los 64 pendientes mencionados corresponden a la réplica auditada; contabilizar la cola real antes de habilitar workers. Publicar desde un directorio nuevo (`release/stage13-backend-final`) para evitar arrastrar DLL de scaffolding retiradas. Resolver el gate de dependencias antes de considerar el despliegue.
